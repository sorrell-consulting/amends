# Synthetic specification fixtures

These files specify the [correction walkthrough](../docs/evaluation.md). They are not a test execution result, a broker dump, or a production record.

Inventory starts at 100 units. A receipt adds stock and an issue removes it; the daily close is the inventory remaining after that day's active movements. Issues of 50 and 20 units, then a receipt of 50, give closes of 50, 30, and 80 units on Days 1–3. The reorder threshold is 60 units. Falling from at least 60 to below 60 creates a downward-crossing alert, so Day 1's fall from 100 to 50 qualifies; staying below 60 on Day 2 does not.

Replacing the first issue with 30 units changes the closes to 70, 50, and 100. Day 1 no longer qualifies; Day 2's fall from 70 to 50 now does. The original Day 1 alert must be withdrawn and a Day 2 alert published. Slash-separated balances below always list successive daily closes in inventory units.

Load `config.json` as immutable namespace configuration, then `before.jsonl` for the initial result. `correction.jsonl` contains the one late complete replacement. Compare the business projections to `expected-before.json` and `expected-after.json` respectively.

Optionally append `cancel-last-day.jsonl` to withdraw the final active transaction on Day 3 and compare to `expected-after-cancel.json`. Balance rows exist only for days with active transactions: Day 3's row disappears, and the preceding balance carries forward implicitly rather than becoming zero. The consumer retains the deletion version (a tombstone) so an older delayed statement cannot restore the removed row.

Expected outputs are independently specified arithmetic values. They intentionally do not fix message histories, output version counts, transport offsets, or namespace IDs. Tests must check those separate delivery/namespace invariants without assuming one required publication history.

These files are embedded by `fixtures/embed.go`. `make core-demo` and the scenario tests check the original expected projections independently against the oracle and memory view. The source records and hand-calculated expected JSON files are not generated by either algorithm.

## Diagnostic drills

The diagnostic drills first load `before.jsonl` and `correction.jsonl`, then append one of these finite sequences:

| Sequence | Hand-derived observation |
| --- | --- |
| `poison-event.jsonl` | Revision zero is rejected with reason `REVISION`; 70/50/100 and the Day 2 alert remain unchanged |
| `poison-repair.jsonl` | A valid revision 1 for the rejected identity issues 10 units on Day 3; closes are 70/50/90 and the Day 2 alert remains |
| `source-conflict.jsonl` | ISSUE-001 revision 2 now asserts both -30 and -40; DEMO-PART becomes BLOCKED with its previous numerical outputs frozen; DEMO-OTHER independently closes at 75 |
| `conflict-repair.jsonl` | Unique revision 3 asserts -20; closes become 80/60/110, no crossing remains, and READY follows the business repair |

`conflict-other-key.json` adds the second key to the fresh manifest **before** any processing namespace is created. Both keys map to partition zero; opening balance and threshold are 100 and 60. No existing immutable configuration is edited. The `expected-*-repaired.json` and `expected-conflict-other.json` files state the business expectations independently.

On these fresh nontransactional fixture topics, poison is at source offset 4; conflicting revision-2 records are at offsets 3 and 4. The runner builds exact named diagnostic manifests from these declared bytes, keys, coordinates, and reason/identity, never from observed verifier answers. A valid replacement does not erase the rejected record or historical conflict. Final verification remains `PASS_WITH_EXCLUSIONS`.

## Duplicate and stale-input drills

These sequences follow the original `before.jsonl` and `correction.jsonl`:

| Fixture | Hand-derived observation |
| --- | --- |
| `duplicate-deliveries.jsonl` | ISSUE-001 revision 2 is delivered with its original SourceTime and again with SourceTime in 2050; both are the same canonical -30 amendment |
| `stale-protection.jsonl` | ISSUE-001 revision 4 retains -30 without restating outputs; RECEIPT-003 revision 3 cancels Day 3, leaving closes 70/50 and the Day 2 crossing |
| `stale-deliveries.jsonl` | Previously unseen ISSUE-001 revision 3 asserts -40 and RECEIPT-003 revision 2 asserts +50, both with SourceTime in 2050; neither replaces higher authority or resurrects Day 3 |

The duplicate drill repeats its two-line file 64 times (128 deliveries). The stale drill first loads protection, then its two unseen amendments once, then repeats those amendments 64 times (130 stale deliveries in total). Repetitions preserve canonical payloads while changing source coordinates. Repeating stale candidates is both duplicate and stale, so a single delivery can contribute to both counters. No equal-revision conflict is introduced.

Expected business values are in the hand-derived `expected-after.json` and `expected-after-cancel.json`. Fixed output versions, frontier vectors, retained evidence, and unchanged byte-level output/view state are checked separately. The finite expanded input and its SHA-256 are retained with each run; expected values are not generated from the implementation.

## Rebalance with two populated partitions

`rebalance-other-key.json` declares DEMO-SECOND at DEPOT-A on partition one, with opening balance 100 and threshold 60, before creating the fresh namespace. DEMO-PART remains on partition zero. `rebalance-before.jsonl` interleaves three records for each key: Day 1 issue -50, Day 2 issue -20, and Day 3 receipt +50. Each independently closes at 50/30/80 with the Day 1 crossing.

`rebalance-correction.jsonl` contains one complete revision-2 replacement per key, changing its Day 1 issue to -30. Each independently closes at 70/50/100 with only the Day 2 crossing. The drill repeats this two-line file 32 times, leaving 35 retained source records per partition. The additional repeats are duplicate assertions and leave business values unchanged. Input production finishes before the group expands; queued corrections remain on both partitions during reassignment.

`expected-rebalance-other-before.json` and `expected-rebalance-other-after.json` state this second key's arithmetic explicitly. DEMO-PART uses `expected-before.json` and `expected-after.json`. Oracle and durable-view checks independently compare against these hand-stated values; exact source/output boundaries, versions, and retained alert deletions are separate fixture-specific assertions. The expanded burst and its hash are retained with the run. This finite backlog is not a load benchmark.
